# V19.5.13 — Authorization Blocker Resolution

## Decisions

1. The V1 route plan is registered in `contracts/astro/route-inventory.yaml` (96 planned route templates, including dynamic route templates).
2. The documented Admin surface has an exact route registry in `contracts/permissions/admin-rbac.json` (53 routes at this revision). This is exhaustive for currently documented V1 Admin routes; new Admin routes must add an entry before implementation.
3. Each Admin route specifies capability, allowed role families, scope, risk, approval requirement and safe projection.
4. Session validation, cookie controls, CSRF, safe return-to, revocation, policy outage and authorization error behavior are specified in `contracts/security/authentication-session-runtime.yaml`.
5. Cross-boundary positive and negative authorization cases are registered in `contracts/security/authorization-acceptance-matrix.yaml`.
6. `pnpm validate:authorization` checks inventory/RBAC parity and required security contract invariants.

## What is resolved

The design-level blockers are resolved: there is now an explicit intended route inventory, an exact Admin RBAC registry for the currently documented V1 scope, a session/runtime contract, and a required acceptance matrix.

## What is not claimed

This is a planning/contract update, not an implementation. The repository currently contains a minimal Astro starter route; it does not contain all 96 planned route files. The route inventory must be compared to actual files after the official Astro scaffold and route implementation. Authentication middleware, backend authorization and tests remain unimplemented until code and test evidence exist. Do not mark production-ready based on YAML validation or registry completeness alone.

## Implementation gate

The implementation agent must:

- Scaffold using the official Astro CLI and preserve platform-generated structure.
- Implement only registered route templates or submit an explicit contract change first.
- Compare generated route files to the planned inventory and block unexplained differences.
- Enforce authorization in middleware and again at each authoritative backend operation.
- Pass every applicable case in the authorization acceptance matrix, including direct-call bypass and cross-tenant access tests.
- Produce test evidence and update runtime implementation status only after those tests pass.
