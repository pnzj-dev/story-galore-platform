# V19.5.11 — Independent Route Authorization

## Decision

Keep one Astro application and one Appwrite Site. Separate security policy by registered route group; do not create extra applications merely to protect route surfaces differently.

## Route classes

- Public: authentication optional; public policy still applies.
- Authenticated: valid Appwrite session and a registered capability.
- Creator/Studio: authenticated creator access plus resource/tenant ownership policy.
- Admin: authenticated explicit admin access plus route-specific capability.
- Route-specific overrides may strengthen, but not weaken, parent policy without an approved contract change.

## Enforcement

Astro middleware performs early session and policy checks before protected content is rendered. It is not the final authority. Every Astro Action, API endpoint, backend command, Appwrite Function, Agent tool and MCP tool independently checks the registered capability at its authoritative execution boundary. Direct requests cannot bypass these checks.

Do not trust client-supplied role/capability claims. A session does not imply creator or administrator access. Missing or ambiguous mappings, unknown capabilities, unavailable policy evaluation, and conflicting rules fail closed. API/mutation requests use contract-defined authorization errors rather than browser redirects.

## Canonical contracts

- `contracts/astro/routes.yaml` — route rendering and protection registry.
- `contracts/astro/route-protection.yaml` — protection semantics and fail-closed rules.
- `contracts/astro/middleware.yaml` — middleware pipeline and security boundary.
- `contracts/security/authorization-completeness.yaml` — cross-system authorization completeness.

## Validation

Run `pnpm validate:astro-appwrite` and `pnpm validate:determinism`. Concrete routes added during implementation must be checked against the route registry; this contract does not grant broad access simply because a path matches a public-looking prefix.
