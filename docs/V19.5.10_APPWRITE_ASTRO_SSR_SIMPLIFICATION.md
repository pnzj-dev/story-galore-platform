# V19.5.10 — Canonical Astro SSR on Appwrite Sites

## Purpose

V19.5.10 resolves the web-hosting ambiguity and removes the obsolete two-site model.

StoryGalore uses **one Astro web application** deployed as **one canonical Appwrite Site**.

The Astro application uses the official `@astrojs/node` adapter for SSR. Appwrite Sites' `adapter: ssr` setting selects the Site rendering mode; it is not a separate `@astrojs/appwrite` package.

## Canonical path

```text
apps/web
  ↓
Astro
  ↓
@astrojs/node
  ↓
Appwrite Sites (framework: astro, adapter: ssr)
```

## Route surfaces

Public, Creator Studio and Admin are product surfaces implemented as routes within the same Astro application. They are not separate Astro applications and not separate Appwrite Sites.

Security, authorization, layout, navigation and route contracts remain explicit; a shared application does not imply shared permissions.

## Rendering

The Appwrite Site is SSR-capable by default. Individual Astro routes select `PRERENDER` or `ON_DEMAND` according to their route contract.

Static editorial content should be prerendered when build-time stable. Authenticated, personalized and protected routes remain on-demand unless a contract explicitly permits prerendering.

## Deployment

The official Appwrite CLI is authoritative for Appwrite Site scaffolding/configuration. The official Astro CLI is authoritative for the Astro application scaffold. The repository must not invent platform-specific generated structure.

The repository may commit the inspected generated `appwrite.config.json` representation only after the CLI output and current Appwrite Site schema have been validated.

## Determinism

A coding agent MUST block if:

- the Appwrite Site SSR capability cannot be verified;
- the current Astro Node adapter contract is unknown;
- the Site root/build/output configuration is ambiguous;
- a second web Site is proposed without an approved ADR;
- a different hosting platform is introduced without an approved ADR.
