# V18.1 — Execution Resilience

## Objective

Use Cloudflare Workflows as the preferred executor for eligible durable jobs, while maintaining an independent Appwrite-based durable execution path that can operate when Cloudflare is unavailable. Keep Cloudflare Workflows for complex long-running workflows.

## Deterministic execution classes

### IMMEDIATE

Normal request/application execution. No durable job and no Cloudflare Workflows workflow.

### DURABLE_JOB

Use for retryable, idempotent, short/medium background work that does not require complex workflow orchestration.

- PRIMARY: Cloudflare Workflows.
- Appwrite TablesDB stores operation/domain state; it is not an execution worker or failover engine.
- SECONDARY worker: Appwrite Functions.
- Job state is authoritative in Appwrite TablesDB.
- Automatic failover is allowed only when operation idempotency and external-side-effect ownership are safe.

### DURABLE_WORKFLOW

Use Cloudflare Workflows for complex, long-running, multi-step orchestration, including AI pipelines, large media processing, payment/reconciliation workflows, subscription renewals, migrations/backfills, and operations requiring complex signals/compensation.

## Appwrite operation state

`operations` is the source of truth for secondary durable jobs. An Appwrite Function claims a job with a lease, performs the work, heartbeats when needed, and records the terminal result. Functions never own durable job state outside Appwrite.

Required properties:

- operationId
- idempotencyKey
- attempt/maxAttempts
- availableAt
- leaseOwner/leaseUntil
- deterministic state machine
- safe payload reference rather than secrets
- retry/dead-letter semantics

An expired lease returns the job to `QUEUED`; it does not create a new logical operation.

## Failover

Cloudflare Workflows is not treated as infallible. Health state is provider-specific. A primary outage makes eligible DURABLE_JOB operations available to the Appwrite secondary path only when the operation has not acquired an unsafe external side effect elsewhere.

Do not automatically duplicate:

- payment captures
- refunds
- entitlement extensions
- irreversible provider operations
- external actions without idempotency guarantees

These operations use Cloudflare Workflows or controlled reconciliation.

## Coding-agent rules

1. Every asynchronous command MUST declare an execution class.
2. Do not introduce Cloudflare Workflows merely because work is asynchronous.
3. Do not introduce a durable job for ordinary CRUD.
4. Do not call Cloudflare Workflows directly from domain code; use the Execution Dispatcher.
5. Do not call Appwrite Functions directly from domain code; use the Execution Dispatcher.
6. Do not implement business semantics in an executor adapter.
7. Operation/domain state is authoritative in Appwrite TablesDB.
8. Appwrite Functions are stateless workers over the Job Store.
9. Automatic failover requires operationId + idempotencyKey and a safe side-effect classification.
10. Cloudflare Workflows remains the executor for DURABLE_WORKFLOW.

## Availability principle

The secondary execution path must remain operational if Cloudflare is unavailable. It therefore MUST NOT depend on Cloudflare DNS, Cloudflare Queues, Cloudflare Workers, Cloudflare KV, or Cloudflare Workflows for job state or dispatch.
