# V19.5.17 — Deterministic Appwrite MCP Agent Access

## Decision

All autonomous StoryGalore agents use one central Agent Gateway and Policy Engine to reach Appwrite through the registered Appwrite MCP connection. Agent identity is derived from the trusted runtime, not model-generated input. Each agent has a deny-by-default allowlist of stable StoryGalore tool IDs. Native Appwrite MCP tool names are discovered, snapshotted, schema-checked, and mapped only after official catalog verification.

The official Appwrite MCP service is documented at https://appwrite.io/docs/tooling/ai/mcp-servers and hosted at `https://mcp.appwrite.io/`. Appwrite documents OAuth for interactive clients. This does not by itself establish that its hosted OAuth flow supports unattended autonomous runtime identity, per-agent delegation, least-privilege scopes, or revocation guarantees. Those behaviors remain a hard blocker until verified by official documentation and tests.

## Boundaries

- Autonomous agent -> Agent Gateway -> Policy Engine -> Appwrite MCP client/connection -> Appwrite MCP server -> Appwrite.
- External client -> Cloudflare MCP ingress -> same Agent Gateway/Policy Engine -> Appwrite MCP connection. No parallel direct-Appwrite implementation is allowed.
- Normal Astro and Go application code may use their explicitly registered native SDK/API integration paths; this agent-only MCP rule does not force ordinary web requests through MCP.
- Appwrite's native permissions and StoryGalore domain authorization remain mandatory. MCP tool visibility is not an authorization grant.
- Cloudflare Workflows carry identifiers and operation references, not secrets or full authoritative business records. Durable side effects use registered activities.

## Identity and safety

- No shared unrestricted human OAuth session or shared administrator API key.
- No per-agent key proliferation unless the provider contract explicitly requires and safely supports it; the default is a trusted gateway with per-agent policy enforcement plus a least-privilege backend identity.
- Never trust agent-supplied `agentId`, tenant, role, capability, or approval claims.
- Tool discovery is metadata only. Every native tool maps to a stable StoryGalore tool ID, schema, capability, risk class, resource scope, idempotency policy, audit event, and test suite.
- Unknown identity, tool, schema, scope, policy result, or authentication mode => deny and audit.
- Mutations require idempotency; dangerous, financial, permission-changing, or production operations require their registered approval workflow.

## Implementation gates

1. Capture official Appwrite MCP tool catalog and record endpoint, server revision/version if available, timestamp, and SHA-256.
2. Verify unattended authentication/delegation, least privilege, token lifetime/rotation, and revocation. If unsupported, evaluate the official self-hosted server only through a reviewed architecture exception; do not bypass MCP.
3. Populate `contracts/integrations/appwrite-mcp-tool-registry.yaml` with exact verified native tool mappings.
4. Complete and test all per-agent allowlists in `contracts/integrations/agent-appwrite-tool-allowlists.yaml`.
5. Test direct SDK/HTTP bypass denial for agents, tenant isolation, data projections, idempotency, audit, policy outages, and credential revocation.
6. Only then mark the connection `READY` and unblock runtime implementation.

## Explicitly not claimed

This change defines the required architecture and blockers. It does not claim that a deployed gateway, MCP connection, authentication adapter, or runtime authorization enforcement already exists.
