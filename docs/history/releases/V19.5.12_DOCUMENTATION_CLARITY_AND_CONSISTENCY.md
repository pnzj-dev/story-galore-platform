# V19.5.12 — Documentation Clarity and Consistency

## Status

This release repairs contradictions and makes implementation blockers explicit. It does **not** claim that application authentication/authorization has been implemented or that every product route is already specified.

## Canonical web architecture

- Exactly one Astro application: `apps/web/`.
- Exactly one canonical Appwrite Site.
- Astro SSR uses `@astrojs/node`; Appwrite Sites uses `framework: astro` and `adapter: ssr`. These are distinct settings.
- Public, Creator Studio and Admin are route surfaces inside the same application, not separate apps or Sites.
- The public/Creator/Admin labels are product/UI surfaces; they do not create security boundaries.

## Authorization semantics

1. `contracts/astro/routes.yaml` declares route-policy templates and the source from which concrete Astro routes are enumerated. It is not a substitute for the concrete route inventory.
2. Every concrete route must resolve to exactly one effective policy. A missing or ambiguous mapping blocks implementation.
3. `contracts/permissions/route-access.yaml` declares baseline user/creator route capabilities and scope requirements. It does not grant capabilities to users.
4. `contracts/permissions/admin-rbac.json` currently defines the admin RBAC schema and examples, not a complete admin route registry. Its status explicitly blocks implementation of admin routes until every concrete admin route is registered.
5. Astro middleware verifies session context and performs early policy gating. It is not the final authority. Every Astro Action, API endpoint, backend command, Appwrite Function, Agent tool and MCP tool must independently enforce its own registered capability at the authoritative execution boundary.
6. The UI may hide unavailable actions but never grants access. Client-supplied actor IDs, roles, capabilities and entitlement claims are untrusted.
7. Route authorization does not replace resource ownership, tenant isolation, entitlement, age, jurisdiction, moderation or approval policies.

## Cross-document corrections

- Removed duplicate-path wording caused by the former two-app model.
- Updated README and architecture diagrams to describe one app and one Site.
- Corrected the Appwrite backend language statement: Go for Appwrite Functions/backend; TypeScript remains at frontend and registered Cloudflare platform boundaries. Astro SSR code is part of the web application runtime, not an Appwrite Function.
- Marked the V18.1 secondary durable executor design as historical/superseded. Cloudflare Workflows is the sole V1 durable workflow engine under V19.5.4+.
- Added `docs/README.md` as the documentation source hierarchy and first-read guide.
- Added `scripts/validate-doc-consistency.mjs` and `pnpm validate:docs`.

## Required tests before implementation is considered ready

- Enumerate all concrete Astro route files and require exactly one effective route policy per route.
- Require exact admin route registration for every implemented `/admin` route.
- Verify capability identifiers exist in the canonical registry.
- Test anonymous, authenticated non-creator, creator-without-resource-access, creator-with-resource-access, staff-without-capability, and admin-without-route-capability cases.
- Attempt direct calls to Astro Actions, API endpoints, Appwrite Functions, Agent tools and MCP tools; they must enforce authorization independently.
- Test expired/revoked sessions, missing actor context, unavailable policy evaluation, conflicting policies, cross-tenant identifiers, and unauthorized mutations.
- Test that route additions without a contract mapping fail CI.

## Validation boundary

Documentation consistency and YAML/JSON syntax checks prove only that the repository's specifications are structurally coherent. They do not prove runtime security, Appwrite provider behavior, or production readiness. Those require implementation-level tests and platform validation.
