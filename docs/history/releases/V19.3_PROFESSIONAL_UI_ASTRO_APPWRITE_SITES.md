# V19.3 — Professional UI, Astro-Native Architecture & Appwrite Sites Execution Kit

## Purpose

V19.3 adds a deterministic implementation layer for professional UI quality and Astro-first web architecture while making Appwrite Sites the canonical web hosting target.

## Hard rule

The coding agent MUST NOT guess visual design, rendering strategy, hydration, routing, content storage, image handling, or hosting behavior when a V19.3 contract exists.

Decision order:

1. Read `DESIGN.md`.
2. Read applicable UI contracts under `contracts/ui/`.
3. Read applicable Astro contracts under `contracts/astro/`.
4. Read Appwrite Sites contracts under `contracts/appwrite/sites/`.
5. Follow existing domain/authorization contracts.
6. If a required decision is missing or ambiguous, STOP with `MISSING_CONTRACT` or `AMBIGUOUS_REQUIREMENT`.

## Professional UI

StoryGalore has three visual surfaces:

- Public: cinematic, editorial, artwork-first.
- Creator Studio: professional creative tooling, high information density, persistent workspace controls.
- Admin: operational analytics and management console, very high information density.

They share primitives and semantic tokens but have different density profiles.

Every reusable component must support the states, themes, directions, responsive modes, keyboard behavior and visual regression requirements in the UI contracts.

## Astro-first architecture

Astro is the default rendering and composition layer. Svelte 5 is an island framework, not the default page framework.

Use Astro-native capabilities whenever they satisfy the requirement:

- file-based routing
- layouts
- Content Collections
- Markdown/MDX
- `astro:assets`
- View Transitions / current Astro client-router facilities where appropriate
- Astro Actions
- middleware
- endpoints where an explicit HTTP contract requires them
- prerendering
- on-demand rendering
- server islands when contractually useful
- safe navigation prefetching

Do not create a custom router or a global client-side application shell unless an explicit architecture decision changes this rule.

## Rendering

The single `apps/web` application targets one Appwrite Site using Astro SSR with the official Astro Node adapter. The application defaults to server rendering so authenticated/personalized routes are available; individual routes may be prerendered when their data and policy contracts permit it.

The agent MUST decide rendering per route. Static content should be prerendered when it is genuinely build-time stable. Protected or personalized content must remain on-demand unless explicitly contracted otherwise.

## Content Collections and Markdown

Content Collections are for repository-backed editorial content such as posts, guides, announcements, help and changelog entries. Appwrite remains authoritative for runtime domain state. The agent must not silently mirror Appwrite domain entities into Content Collections.

Creator posts may use Markdown/MDX only where the product/content contract explicitly chooses repository-backed editorial semantics.

## Images

Use `astro:assets` for site-owned editorial/UI imagery. Creator media remains in Appwrite Storage and is delivered through the existing Media Distribution and Policy Engine contracts. Protected media must never become a permanent public URL merely because it is rendered by Astro.

## View Transitions

Navigation should use Astro's current View Transition/client-router capabilities where safe. Transitions must preserve accessibility, focus, reduced-motion behavior, stateful Svelte island lifecycle and authorization boundaries.

## Middleware and Actions

Astro middleware provides request context such as locale, direction, request ID, session context and feature flags. It does not replace the StoryGalore Policy Engine.

Astro Actions are web adapters. Mutations delegate to canonical domain commands, enforce policy and idempotency, and return operation handles for durable work.

## Appwrite Sites

Appwrite Sites is the canonical hosting platform for the web application. Do not introduce Vercel, Netlify, Cloudflare Pages, Firebase Hosting or another web host without an explicit ADR and architecture approval.

The deployment contract uses:

- `apps/web` (one application with public, Creator Studio and Admin route surfaces)
- framework `astro`
- SSR adapter
- Node 22 build runtime
- pnpm frozen-lockfile installation
- site-specific build commands
- `./dist` output
- Git production branch `main`
- non-main branch previews

Site configuration is represented in `appwrite.config.json.example`; real project IDs, site IDs, specifications and secrets remain environment/project configuration and are never invented.

## Security

Appwrite's ephemeral Site API key is treated as privileged server context. It must only be used for server-authorized operations that cannot be authorized as the visitor. Signed-in visitor operations should forward the visitor's session so Appwrite permissions remain effective.

Never expose Appwrite Site API keys, service credentials, payment credentials, BYOK secrets or provider tokens to the browser bundle.

## Release gate

A UI or Astro change is complete only after:

- applicable contract validators pass
- typecheck/build pass
- UI state coverage is complete
- accessibility checks pass
- visual regression checks pass for affected routes
- responsive/theme/RTL checks pass
- Appwrite Sites build configuration remains valid
- no new unauthorized client-side data path is introduced
- production deployment remains behind the existing release authorization gate
